# 篮球正负值复核（FastAPI + SQLite）

同节同秒的换人与得分可能交错发生，导致球员正负值不唯一。本应用上传一场比赛的
**换人 CSV**、**得分 CSV** 与**本方首发五人**，计算每名本方球员正负值（在场时
本方得分 − 对方得分）的**可达最小值 / 最大值**；看录像后可在网页登记同节同秒的
一笔换人和一笔得分谁先发生，系统计入提交时已生效的全部核实后重算，并把核实记录
与重算结果一并写入 SQLite。

## 目录结构

```
app/
  engine.py     # 核心引擎：时刻分组 + 组内动态规划求正负值区间
  csvio.py      # CSV 解析与上传校验（保留两表原始行序）
  database.py   # SQLite 持久化、写锁串行化、锁等待重试
  main.py       # FastAPI 路由
  static/       # 原生 HTML/JS/CSS 页面（无构建步骤）
samples/        # 可直接在网页试用的样例 CSV
tests/          # pytest：引擎单测 + API/并发集成测试（22 个用例）
Dockerfile
docker-compose.yml
```

## CSV 格式

换人 CSV（表头固定）：

| 列 | 含义 |
| --- | --- |
| `period` | 节次（从 1 开始） |
| `remaining` | 该节剩余秒数 |
| `outgoing` | 下场球员 |
| `incoming` | 上场球员 |

得分 CSV（表头固定）：

| 列 | 含义 |
| --- | --- |
| `period` / `remaining` | 节次 / 剩余秒数 |
| `team` | `own`/`opp`（也接受中文 `本方`/`对方`） |
| `points` | 分值，1、2 或 3 |
| `scorer` | 本方得分必填得分者；对方得分留空 |

两表各自必须按比赛进程排列（节次递增、同节剩余秒数不增），同节同秒的记录在表内
保持原始行序；上传时若发现时刻倒退直接拒绝，不做自动重排。

## 运行

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

SQLite 数据文件位于卷 `pm-data` 内的 `/data/plusminus.db`（WAL 模式）。

### 本地直接运行

```bash
pip install -r requirements.txt
PM_DB_PATH=./plusminus.db uvicorn app.main:app --host 0.0.0.0 --port 8000
pytest tests/
```

网页点击「载入样例数据」会自动填入 `samples/` 下的两份 CSV 与首发五人，再点
「上传并计算」即可；也可以通过 `/samples/subs.csv`、`/samples/scores.csv` 下载。

## 计算模型

1. **时刻分组**：所有事件按 `(节次, 剩余秒数)` 分组，时刻之间顺序固定；同组内
   换人之间、得分之间分别保持各自 CSV 行序，换人与得分可以任意交错。
2. **组合法性**：
   * 换人执行时，下场球员必须在场、上场球员必须在场外（与交错无关，静态检查）；
   * 本方得分执行时，得分者必须在场；对方得分无得分者要求；
   * 核实记录给同组内一对（换人，得分）附加确定的先后边。
3. **动态规划**：组内以 `(已执行换人数 i, 已执行得分数 j)` 为状态，场上阵容只由
   `i` 决定。每个状态维护各球员累计正负值的 min/max 向量，沿「执行下一笔换人」
   「执行下一笔得分」两条边转移并做逐元素 min/max 合并，同时统计合法交错顺序数
   （上限 1000 万，超出截断）。各时刻组的区间相加即全场区间。
4. **无解处理**：若数据本身或新增核实后排不出合法顺序，接口返回 400/409 并说明
   原因（哪一节、哪一秒、哪一行、违反哪条规则）；核实登记场景下整个事务回滚，
   已有核实记录与结果保持不变。

## API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/games` | 上传名称、首发与两份 CSV，返回首版区间 |
| `GET` | `/api/games` | 比赛列表（含核实数、合法顺序数、状态） |
| `GET` | `/api/games/{id}` | 详情：时间线、核实记录、最新结果 |
| `POST` | `/api/games/{id}/verifications` | 登记一条同秒先后核实并重算（重复提交幂等；冲突返回 409 且回滚） |
| `GET` | `/samples/{subs,scores}.csv` | 样例文件 |

## 并发与持久化

* 每个 FastAPI 进程内用一把可重入写锁把「插入核实 → 重读全部已生效核实 → 重算 →
  写结果」串行化；每次重算都重新读取当时数据库中**全部**核实记录，因此并发提交
  的效果等价于按某个串行顺序全部生效。
* SQLite 开启 WAL 与 `busy_timeout`，写操作对 `database is locked` 做退避重试，
  多 worker 部署也不会丢提交。
* 表：`games`、`events`、`verifications`、`results`（每比赛一行最新结果）、
  `result_snapshots`（每次有效重算的历史快照，含当时核实数）。

## 实测结果

本地 Python 3.11 + uvicorn 实测（自动化用例见 `tests/`，22 项全部通过）：

* 样例比赛初始共 3 种合法交错，A5 区间 `[-2, 1]`、B1 区间 `[3, 6]`；
  登记「换人 1 先于得分 1」后合法顺序收敛为 1，A5 变为 `[0, 0]`、B1 变为 `[4, 4]`。
* 重复提交同一核实返回 `duplicate=true`，不新增记录。
* 对同一对换人/得分并发登记正反两个方向：一个 200、一个 409，最终核实数与合法
  结果保持一致（冲突事务回滚，旧结果照旧）。
* 三条不同时刻组的核实并发提交：全部 200，快照表记录合法顺序数 8 → 4 → 2 → 1。
* 非法换人（下场者不在场）上传返回 400 并指明行号；CSV 时刻倒退返回 400 且不入库。

## 待办 / 已知限制

* 运行环境未安装 Docker，Dockerfile 与 Compose 已交付但未在本机实际构建验证，
  仅用 uvicorn 直接运行完成实测；首次在有 Docker 的机器上建议先
  `docker compose config` 校验。
* 目前只建模本方球员名单与本方换人；对方阵容、对方换人不影响本方正负值，未入库。
* 未做账号体系与多人编辑权限，所有访问者均可登记核实（适合单队内部复核场景）。
* 同秒事件规模按真实比赛量级设计（每组通常个位数），未针对超大分组做专门压测；
  状态数上界为组内换人/得分数的网格规模，极端数据下需要再评估。
* 暂无事件级编辑/删除接口，录入错误目前需要重新上传比赛。
