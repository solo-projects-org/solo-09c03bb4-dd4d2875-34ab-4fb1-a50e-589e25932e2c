# 篮球正负值复核（FastAPI + SQLite）

同节同秒的换人与得分可能交错发生，导致球员正负值不唯一。本应用上传一场比赛的
**换人 CSV**、**得分 CSV** 与**本方首发五人**，计算每名本方球员正负值（在场时
本方得分 − 对方得分）的**可达最小值 / 最大值**；看录像后可在网页登记同节同秒的
一笔换人和一笔得分谁先发生，系统计入提交时已生效的全部核实后重算，并把核实记录
与重算结果一并写入 SQLite。

## 目录结构

```
app/
  engine.py     # 核心引擎：时刻分组 + 组内动态规划求正负值区间
  csvio.py      # CSV 解析与上传校验（保留两表原始行序）
  database.py   # SQLite 持久化：BEGIN IMMEDIATE 跨进程串行、只读快照事务、快照修复
  main.py       # FastAPI 路由
  static/       # 原生 HTML/JS/CSS 页面（无构建步骤）
samples/        # 可直接在网页试用的样例 CSV
tests/          # pytest：引擎单测 + API/并发集成测试（38 个用例）
                # manual_smoke_multiworker.py：双 uvicorn 进程冒烟脚本（手动运行）
Dockerfile
docker-compose.yml
```

## CSV 格式

换人 CSV（表头固定）：

| 列 | 含义 |
| --- | --- |
| `period` | 节次（从 1 开始） |
| `remaining` | 该节剩余秒数 |
| `outgoing` | 下场球员 |
| `incoming` | 上场球员 |

得分 CSV（表头固定）：

| 列 | 含义 |
| --- | --- |
| `period` / `remaining` | 节次 / 剩余秒数 |
| `team` | `own`/`opp`（也接受中文 `本方`/`对方`） |
| `points` | 分值，1、2 或 3 |
| `scorer` | 本方得分必填得分者；对方得分留空 |

两表各自必须按比赛进程排列（节次递增、同节剩余秒数不增），同节同秒的记录在表内
保持原始行序；上传时若发现时刻倒退直接拒绝，不做自动重排。

## 运行

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

Compose 以 `--workers 2` 启动**两个 uvicorn 工作进程**，共用卷 `pm-data` 里的
同一个 SQLite 文件 `/data/plusminus.db`（WAL 模式），即多进程并发部署形态。

### 本地直接运行

```bash
pip install -r requirements.txt
PM_DB_PATH=./plusminus.db uvicorn app.main:app --host 0.0.0.0 --port 8000
pytest tests/
```

网页点击「载入样例数据」会自动填入 `samples/` 下的两份 CSV 与首发五人，再点
「上传并计算」即可；也可以通过 `/samples/subs.csv`、`/samples/scores.csv` 下载。

## 计算模型

1. **时刻分组**：所有事件按 `(节次, 剩余秒数)` 分组，时刻之间顺序固定；同组内
   换人之间、得分之间分别保持各自 CSV 行序，换人与得分可以任意交错。
2. **组合法性**：
   * 换人执行时，下场球员必须在场、上场球员必须在场外（与交错无关，静态检查）；
   * 本方得分执行时，得分者必须在场；对方得分无得分者要求；
   * 核实记录给同组内一对（换人，得分）附加确定的先后边。
3. **动态规划**：组内以 `(已执行换人数 i, 已执行得分数 j)` 为状态，场上阵容只由
   `i` 决定。每个状态维护各球员累计正负值的 min/max 向量，沿「执行下一笔换人」
   「执行下一笔得分」两条边转移并做逐元素 min/max 合并，同时统计合法交错顺序数
   （上限 1000 万，超出截断）。各时刻组的区间相加即全场区间。
4. **无解处理**：若数据本身或新增核实后排不出合法顺序，接口返回 400/409 并说明
   原因（哪一节、哪一秒、哪一行、违反哪条规则）；核实登记场景下整个事务回滚，
   已有核实记录与结果保持不变。

## API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/games` | 上传名称、首发与两份 CSV，返回首版区间 |
| `GET` | `/api/games` | 比赛列表（含核实数、合法顺序数、状态） |
| `GET` | `/api/games/{id}` | 详情：时间线、核实记录、最新结果 |
| `POST` | `/api/games/{id}/verifications` | 登记一条同秒先后核实并重算（重复提交幂等；冲突返回 409 且回滚） |
| `GET` | `/samples/{subs,scores}.csv` | 样例文件 |

## 并发与持久化

* **写事务跨进程串行**：每条核实的「查重 → 插入 → 重读全部已生效核实 → 重算 →
  写结果 + 快照」放在同一个 `BEGIN IMMEDIATE` 事务里（进程内另有一把写锁）。
  两个 worker 进程共用 SQLite 时，核实事务只可能按某个串行顺序生效。
* **重传只回读**：已生效核实的重复提交命中 `verifications` 的唯一约束
  （`INSERT OR IGNORE`），不重算、不写库，只回读已提交结果并返回
  `duplicate=true`；并发登记同一条新核实时也只有一次生效，其余按重传返回，
  不会因唯一约束冲突报 500，更不会把别的进程刚收窄的结果覆写回旧值。
* **读一致性**：详情 / 列表的读取包在单个只读事务里，核实清单、球员正负值
  区间与合法顺序数始终对应同一次提交；WAL 下读者不被写事务阻塞，新核实尚在
  重算时读到的是最近已提交的一版。
* **冲突回滚**：登记后算不出合法顺序（如与已有核实互斥）时整个事务回滚，
  返回 409，已提交的核实与结果保持不变。
* **旧库修复**：早期版本的重传可能把 `results` 覆写回更宽的旧区间。
  `result_snapshots` 保存了每次有效核实（含建赛首版）的结果快照，`init_db`
  启动时把每场最新快照与 `results` 比对，不一致则按快照修复——即恢复到最后
  一条有效核实生效时的结果，列表与详情一致。修复幂等，每个 worker 启动都会
  执行。
* 表：`games`、`events`、`verifications`、`results`（每比赛一行最新结果）、
  `result_snapshots`（每次有效重算的历史快照，含当时核实数）。

## 本次修复内容（并发一致性）

1. `get_game_detail` / `list_games` 改为单只读事务：修复详情把新算的正负值
   配给旧核实清单的混搭读。
2. `add_verification` 重构：`BEGIN IMMEDIATE` 跨进程串行化；重传命中唯一
   约束后只回读已提交结果，不再重算覆写，修复双 worker 下重传把收窄结果改回
   旧值的问题。
3. 并发登记同一条核实：由唯一约束原子判重，一次生效、其余按重传返回，消除
   唯一约束冲突导致的 500。
4. `init_db` 增加按最新快照修复 `results` 的旧库升级逻辑。
5. `docker-compose.yml` 以 `--workers 2` 启动两个工作进程，复现并验证多进程
   部署。

## 实测结果

本地 Python 3.11 + uvicorn 实测（自动化用例见 `tests/`，38 项全部通过）：

* 样例比赛初始共 3 种合法交错，A5 区间 `[-2, 1]`、B1 区间 `[3, 6]`；
  登记「换人 1 先于得分 1」后合法顺序收敛为 1，A5 变为 `[0, 0]`、B1 变为 `[4, 4]`。
* 重复提交同一核实返回 `duplicate=true`，响应体就是已提交结果，不新增记录、
  不写库。
* 对同一对换人/得分并发登记正反两个方向：一个 200、一个 409，最终核实数与合法
  结果保持一致（冲突事务回滚，旧结果照旧）。
* 三条不同时刻组的核实并发提交：全部 200，快照表记录合法顺序数 8 → 4 → 2 → 1。
* 非法换人（下场者不在场）上传返回 400 并指明行号；CSV 时刻倒退返回 400 且不入库。
* 交错查询：用可控时序让一次有效核实恰好落在详情读取的两条 SELECT 之间，
  详情仍是同一快照（旧清单配旧结果）；新核实重算未提交期间，并发读始终看到
  最近已提交版本（`tests/test_concurrency.py`）。
* 双进程（`multiprocessing`，共用同一 SQLite 文件）：重传已生效核实赶上另一
  进程提交新核实，收窄结果不被改回，重传回读到收窄后的已提交结果；两进程并发
  登记同一条核实，恰好一次生效、另一次按重传返回，无唯一约束报错。
* 旧库恢复：把 `results` 直接改回首版宽区间（模拟旧版本重传覆写）后执行
  `init_db`，列表与详情均恢复为最后一条有效核实的结果，重复执行幂等。
* 双 uvicorn 进程冒烟（`python3 tests/manual_smoke_multiworker.py`，等价于
  Compose 的 `--workers 2` 形态）：网页可打开；核实流进行中并发读详情/列表
  无混搭；30 轮「重传 vs 新核实」库内结果始终为收窄值；30 轮双进程并发同一
  核实均只生效一次；矛盾核实 409 且数据不变；停机污染 `results` 后重启即修复。
  同一脚本在修复前代码上复现了全部三类故障（详情混搭、20/30 轮结果被改回、
  并发同核实 500）。

* 未做账号体系与多人编辑权限，所有访问者均可登记核实（适合单队内部复核场景）。
* 同秒事件规模按真实比赛量级设计（每组通常个位数），未针对超大分组做专门压测；
  状态数上界为组内换人/得分数的网格规模，极端数据下需要再评估。
* 暂无事件级编辑/删除接口，录入错误目前需要重新上传比赛。
